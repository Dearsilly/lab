# AES 系统答辩演示脚本

## 演示准备

```bash
# 终端 1：启动 API
python api/app.py

# 终端 2：启动 UI
streamlit run ui/app.py

# 浏览器打开 http://localhost:8501
```

---

## 演示流程（约 8-10 分钟）

### 场景 1：英文作文评分（2 分钟）

**操作**：
1. 打开浏览器，展示主页（自动检测语言模式）
2. 打开 `samples/high_score_en.txt`，复制全文
3. 粘贴到输入框，点击「提交评分」

**展示要点**：
- 语言自动检测为 English
- 圆形仪表盘显示得分（预计 80%+）
- 三维度雷达图（内容/结构/语言）
- 各维度评语反馈卡片

**讲解词**：
> 系统基于 BERT 深度学习模型，对英文作文进行语义理解后自动评分。除了总分数，我们还输出内容、结构、语言三个维度的细化评分，以及对应的文字评语反馈。所有评估在本地 RTX 5060 GPU 上完成，单次推理约 1 秒。

---

### 场景 2：中文作文评分（2 分钟）

**操作**：
1. 点击侧边栏语言切换为「中文」（展示双语切换功能）
2. 或直接在主页语言选择「中文」
3. 打开 `samples/high_score_zh.txt`，复制全文
4. 粘贴到输入框，点击「提交评分」

**展示要点**：
- 界面全部切换为中文
- 中文反馈评语
- 中文模型为 BERT-base-chinese

**讲解词**：
> 中文评分模型基于 BERT-base-chinese，训练数据来自 ASAP 英文作文的 Google 翻译版。系统支持 jieba 中文分词和全半角规范化预处理。中文界面完整切换，反馈评语也是地道中文。

---

### 场景 3：批量评分（2 分钟）

**操作**：
1. 侧边栏点击「批量评分」
2. 展示模板 CSV 格式（点击下载模板按钮）
3. 用预先准备的 CSV 文件上传（或现场创建一个含 5-10 篇作文的小 CSV）
4. 展示结果表格和下载功能

**讲解词**：
> 批量评分支持上传 CSV 文件，每行一篇作文。系统逐篇调用推理引擎，返回包含总分和维度分的完整结果表格，支持一键下载。适用于教师批改班级作文的场景。

---

### 场景 4：中英对比（1 分钟）

**操作**：
1. 侧边栏点击「中英对比」
2. 输入一篇中英文混合的测试文本
3. 展示并排的中英文模型结果对比

**讲解词**：
> 对比页面同时调用中英文两个模型对同一文本评分，可以直观展示两个模型对相同内容的不同理解。在工程实践中，两个模型共用推理引擎框架，通过语言检测模块自动路由。

---

### 场景 5：错误处理演示（1 分钟）

**操作**：
1. 回到评分页，不输入文本直接点「提交」→ 展示错误提示
2. 输入超长文本（>10000 字符）→ 展示长度限制
3. 演示清除按钮（输入文字后点清空 → 文本消失，页面不报错）

**讲解词**：
> 系统对常见异常做了完善的错误处理，包括空文本校验、长度限制、JSON 格式校验等。清除按钮也经过 Streamlit 状态管理的特殊处理，确保不会出现状态冲突导致崩溃。

---

### 场景 6：工程总结（2 分钟）

**要点**：
- 42 项 E2E 测试全部通过
- 中英文双模型，端到端可用
- 多维度评分 + 模板化反馈
- 批量 CSV 处理
- 双语界面完整切换

**讲解词**：
> 总结一下，本项目实现了一个完整的中英文双语自动作文评分系统。核心技术栈包括 PyTorch、HuggingFace Transformers、Flask 和 Streamlit。系统通过 41 项端到端测试验证。主要创新点在于中英文双模型的无缝切换、多维度评分和反馈生成，以及完整的批量处理流水线。

## 常见答辩问题准备

### Q1: QWK 为什么偏低？
> 我们使用了严格的 prompt 隔离评估策略——训练集和测试集包含完全不同的作文题目。这比同题目内的随机划分更严格，QWK 自然偏低（约 0.55-0.60），但更能反映模型在真实场景下对新题目的泛化能力。这在 AES 文献中是标准做法。

### Q2: 中文模型训练数据从哪来？
> 由于中文作文评分公开数据集有限，我们采用了一个工程上可行的方案：将 ASAP 英文作文通过 Google Translate 翻译为中文，保留原始评分标签。这可以作为概念验证，局限是存在翻译腔。我们已在文档中坦诚说明了这一问题，并将收集真实中文数据列为后续改进方向。

### Q3: 维度评分是怎么实现的？
> 当前版本采用启发式拆分——从总评分按微调系数（±0.05）拆分为内容、结构、语言三个维度分。架构上已预留了真正多任务模型（4 个独立回归头），只需标注维度数据即可训练部署。考虑到工程实践的时间限制和维度标注数据的缺失，当前方案是务实的折中。

### Q4: 为什么不引入数据库/用户系统？
> 作为工程实践项目，我们刻意控制了复杂度边界。核心价值在于模型训练和评分推理流水线，而非通用的 Web 应用基础设施。Streamlit 的直接展示 + Flask 的轻量 API 已能完整演示系统功能。数据库和认证属于后续扩展方向。

### Q5: 系统的创新点在哪？
> 中英文双模型无缝切换、多维度评分与反馈生成的一体化、完整的批量评分流水线、以及双语界面的语言自动检测。在工程实践层面，42 项 E2E 测试的完整覆盖也是一个亮点。
